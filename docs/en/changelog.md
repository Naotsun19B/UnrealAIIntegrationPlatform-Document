# Changelog

Per-release changes for the UAIP plugin. Before reading the entries below, please skim the **Versioning Policy** section so you know what each version number means (breaking change vs additive vs fix).

---

## Versioning Policy

UAIP follows [Semantic Versioning 2.0.0](https://semver.org/).

### Reading version numbers

A version number is `MAJOR.MINOR.PATCH`.

| Segment | Meaning |
|---|---|
| **MAJOR** (e.g. `1.x.x` → `2.x.x`) | Breaking changes. May require updating command names, parameter shapes, or config files on upgrade |
| **MINOR** (e.g. `1.0.x` → `1.1.x`) | Backward-compatible additions — new commands, new capabilities, new optional parameters. Existing calls keep working |
| **PATCH** (e.g. `1.0.0` → `1.0.1`) | Bug fixes only. No impact on the public API |

### Current phase: 1.x.y (Fab Pro released)

The current version is **1.1.0**. UAIP is **released on Fab as the Pro product** ([listing](https://www.fab.com/listings/0eedf909-00ac-4d95-b109-8fda51800fff)). For the changes since 1.0.0 — the first entry of the `1.x.y` series — see the release list below.

- Standard SemVer rules now apply strictly: breaking changes require a MAJOR bump (e.g. `2.0.0`)
- New commands / new capabilities ship as MINOR (e.g. `1.0.x` → `1.1.0`)
- Bug fixes ship as PATCH (e.g. `1.0.0` → `1.0.1`)

### Pre-1.0 history: 0.x.y series

Versions `0.9.0` and `0.9.1` were demo-only releases distributed via GitHub Releases ahead of the Fab Pro submission. Their entries are preserved below for historical reference.

### Pre-release tags

Pre-release tags are not used in routine development. The only exception is an optional `1.0.0-rc.1`-style RC (release candidate) build distributed via GitHub Releases immediately before Fab submission. An RC build ships **identical code** to what will be submitted to Fab — if no issues are found, the same code is re-tagged as `1.0.0`.

### Deprecation policy (rarely removed)

UAIP maintains a single source tree across UE versions using version macros (not per-version branches). Because of this, **commands shipped to users are not removed once released**.

- Commands scheduled for retirement are marked `Stability: "Deprecated"` but **keep working**
- `uaip_describe_command` exposes the `DeprecationMessage` and `MigrationTarget` (recommended replacement)
- The only exception: when Epic removes an underlying engine API and UAIP can no longer maintain the implementation, the affected command may be removed during a MAJOR bump

This guarantees that older command names — which may be baked into an AI agent's training data or working memory — keep functioning long-term.

### Demo and Pro share the same version number

The free demo (GitHub Releases) and Pro (Fab) **always share the same version number**. Both are built from the same source with only feature gating differences, so HealthCheck's `UAIPVersion` field returns the same value either way.

#### UAIP Plugin

**Added**

- **Asset validation, as a job or in one call** (`UAIPEditorValidation` module, **new**, requires the `DataValidation` plugin; **Pro only** — not available in the demo build): AI agents can now run the asset validators a project has registered, read what they found as structured results, and apply the fixes those validators offered. Adds 7 commands under `UAIP.Editor.Validation` — `ListValidators` (which validators are enabled, and whether material validation can run at all); `ValidateAssets` (up to 8 assets, synchronously, in a single engine call); `StartValidationJob` / `GetValidationJobStatus` / `GetValidationJobResult` / `CancelValidationJob` (a folder or a long list, validated a few assets at a time so the editor stays usable); and `ApplyValidationFix`. Adds 2 DefaultDenied capabilities: `AssetValidation` (running validators — project-supplied code the engine does not forbid from having side effects) and `AssetValidationFix` (rewriting an asset). UAIP defines no quality rules of its own; every judgement comes from `UEditorValidatorSubsystem`. ⚠️ `DataValidation` must be named **explicitly** in the project's `.uproject` or none of these commands are registered, and material validation additionally needs `MaterialValidationPlatforms` configured plus an editor restart. A chunked job's result is not promised to equal validating everything in one call, and fixes only ever come from project-written validators — no validator the engine ships offers one.
- **AnimNotify editing** (`UAIPEditorAnimSequence` module, **new**; **Pro only** — not available in the demo build): AI agents can now add, remove, and edit AnimNotify / AnimNotifyState entries and notify tracks on `UAnimSequence` / `UAnimMontage` / `UAnimComposite` assets, and repair notify guids left unstable after a load. Adds 11 commands under `UAIP.Editor.AnimSequence` — read-only `GetAnimNotifyInfo`, `GetAvailableAnimNotifyClasses`, `GetAnimNotifyClassSchema` (require `EditorInspect`); track management `AddAnimNotifyTrack` / `RemoveAnimNotifyTrack`; notify placement and removal `AddAnimNotify` / `AddAnimNotifyState` / `RemoveAnimNotify`; event field edits `SetAnimNotifyEvent`; a generic per-notify-instance property writer `SetAnimNotifyProperty`; and guid repair `FixupAnimNotifyGuids`. Adds 2 DefaultDenied capabilities: `AnimNotifyEdit` (required by every edit command) and `AnimNotifyReferenceEdit` (required in addition to `AnimNotifyEdit` only when `SetAnimNotifyProperty` writes a property that is — or contains — a hard object/class reference). Built entirely on engine-shipped AnimNotify types — no optional plugin required. Every edit command is rejected while PIE or SIE is active.
- **`SynchronizePoseSearchDatabase`** (`UAIPEditorMotionMatching` module): AI agents can now explicitly merge `PoseSearchBranchIn` animation notify entries into a `UPoseSearchDatabase`'s `AnimationAssets`, since the engine has no reliable event to observe that merge happening on its own. Adds 1 command under `UAIP.Editor.MotionMatching` (requires `PoseSearchAssetEdit`). ⚠️ Calling it in the same request as the referencing animation asset's save can report zero merged entries, because the asset registry's referencer index rebuilds asynchronously after a save; re-issue the call once the save has settled.
- **MetaHuman character editing** (`UAIPEditorMetaHuman` module, **new**, requires the `MetaHumanCharacter` plugin; **Pro only** — not available in the demo build): AI agents can now author MetaHuman characters end to end — create the asset, set body / skin / eye / makeup / head model / face evaluation settings, sculpt the face, conform and fit to target meshes, manage the wardrobe, drive the preview viewport, request cloud rigging and high resolution texture synthesis, and run the asset build pipeline. Adds 56 commands under `UAIP.Editor.MetaHuman` — creation (`CreateMetaHumanCharacter`), body / skin / eyes (`GetBodyConstraints`, `SetBodyConstraints`, `GetBodyShape`, `SetBodyShape`, `GetSkinSettings`, `SetSkinTone`, `GetEyeSettings`, `SetEyeColor`), appearance detail (`SetSkinSettings`, `GetMakeupSettings`, `SetMakeupSettings`, `GetHeadModelSettings`, `SetHeadModelSettings`, `SetEyeSettings`, `GetFaceEvaluationSettings`, `SetFaceEvaluationSettings`), face sculpting (`GetFaceModelCoefficients`, `SetFaceModelCoefficients`, `GetFaceLandmarks`, `TranslateFaceLandmarks`, `CommitFaceState`, `ImportFaceFromDna`, `ImportFaceFromTemplate`, `ImportFaceFromIdentity`, `CompareFaceState`), conforming and fitting (`GetMeshDataForConforming`, `ConformBodyToTarget`, `ConformFaceToTargetMeshes`, `AlignToTargetMeshes`, `RefineVerticesToTarget`, `CommitPosedStateAsAPose`, `FitStateToTargetVertices`, `FitFaceFromBodyWithEyesTeethTemplate`, `FitFaceFromBodyWithEyesTeethDna`, `GetAsyncConformState`), the build pipeline (`RequestTextureSources`, `GetTextureSourceState`, `RequestAutoRigging`, `GetRiggingState`, `CanBuildMetaHuman`, `BuildMetaHuman`), preview (`GetViewportSettings`, `SetViewportSettings`, `RefreshCharacterPreview`), wardrobe (`ListWardrobeSlots`, `ListWardrobeItems`, `GetWardrobeItemInfo`, `AssignWardrobeItem`, `RemoveWardrobeItem`, `ReplaceWardrobeItem`, `GetWardrobeItem`, `SetWardrobeItem`, `SetWardrobeItemPipeline`, `ListItemPipelineClasses`), and session management (`ReleaseEditSession`). Adds 6 DefaultDenied capabilities: `MetaHumanAssetCreate`, `MetaHumanEdit`, `MetaHumanFileImport`, `MetaHumanTextureSynthesis`, `MetaHumanCloudRigging`, `MetaHumanBuild`. Editing commands open an edit session on demand and hold it open, so most reads in this domain are **not** read-only — they require `MetaHumanEdit` and are refused under a read-only safety policy; `GetViewportSettings` is the only exception and needs just `EditorInspect`. ⚠️ `RequestAutoRigging` **uploads the character's face data to Epic's cloud rigging service** and requires a signed-in Epic account and network access. ⚠️ `BuildMetaHuman` occupies the game thread for the entire build (seconds to minutes). The engine shows a progress dialog and keeps redrawing, so the editor stays usable to look at rather than going unresponsive, but no other command runs until the build returns — that is longer than the MCP bridge freeze detection (30 s) and the default command timeout (60 s), so raise `command_timeout_seconds` before calling it, and call `CanBuildMetaHuman` first. 14 of the 56 commands (`GetFaceModelCoefficients`, `SetFaceModelCoefficients`, `ConformFaceToTargetMeshes`, `AlignToTargetMeshes`, `RefineVerticesToTarget`, `GetAsyncConformState`, `CommitPosedStateAsAPose`, `FitFaceFromBodyWithEyesTeethTemplate`, `FitFaceFromBodyWithEyesTeethDna`, `GetMeshDataForConforming`, `AssignWardrobeItem`, `RemoveWardrobeItem`, `ReplaceWardrobeItem`, `RefreshCharacterPreview`) depend on UE 5.8 engine APIs; they are still registered on UE 5.7 but report `Available: false` and return `PolicyViolation` when called. Also adds 9 Toolset bridge commands under `Toolset.Editor.MetaHuman.*` (`BeginEdit`, `EndEdit`, `GetBodyShape`, `SetBodyShape`, `GetSkinTone`, `SetSkinTone`, `GetEyeColor`, `SetEyeColor`, `Create`), delegating to the `MetaHumanGenerator` Python toolset — these require UE 5.8+ with `MetaHumanGenerator` + `ToolsetRegistry` enabled and are not registered at all on UE 5.7.

- **Unreal Insights trace capture and analysis** (`UAIPRuntimeInsights` module, **new**): AI agents can now record an Unreal Insights trace, mark it up while it records, and analyse the capture offline. Adds 11 commands under `UAIP.Runtime.Insights.Trace` — read-only `ListTraceChannels`, `GetTraceStatus`, `ListTraceFiles` plus control `StartTrace`, `StopTrace`, `PauseTrace`, `ResumeTrace`, `SetTraceChannels`, `AddTraceBookmark`, `BeginTraceRegion`, `EndTraceRegion` — and 3 commands under `UAIP.Runtime.Insights.Analysis` (`AnalyzeTrace`, `GetTraceAnalysisStatus`, `GetTraceAnalysisResult`), which are only registered in builds where trace analysis is supported and report `CommandNotFound` elsewhere. Adds 4 capabilities: `RuntimeInsightsInspect` (DefaultAllow) and `RuntimeInsightsControl` / `RuntimeInsightsAttachTraceFile` / `RuntimeInsightsAnalyze` (all DefaultDenied). Adds a new artifact type `Trace`, and 3 SafetyPolicy keys: `AllowExternalTraceAnalysis` / `ExternalTraceDirectory`, which only take effect when **both** are set (they let `AnalyzeTrace` read a `.utrace` captured outside UAIP; symbolic links inside that directory are not resolved, so point it at a directory kept for UAIP alone), and `AllowDisclosingTraceAttachment`, which allows a captured `.utrace` to be handed over as an artifact when the channels it recorded with could have captured host paths, screen content or network addresses (log text stays governed by `AllowLogDump`, and a channel this build does not classify is refused whatever both are set to). A trace is always written to a file under `Saved/Profiling/UAIP/` — no command in the module can send one to a network destination — and the `trace.` prefix is added to the `UAIP.Runtime.World.ExecuteConsoleCommand` deny-list so that route is closed as well; note that `RunEditorPythonScript` still reaches the engine's trace system and is managed through its own capabilities. Channels are classified by what they can disclose, and `StartTrace` is rejected with `PolicyViolation` when the effective channel set (already enabled ∪ requested) records log text while `AllowLogDump` is false. Analysis is asynchronous with one run at a time; a request that arrives while another run is parsing or extracting is rejected with `TooManyRequests` naming the `AnalysisId` of the run holding the slot, so it can be watched through `GetTraceAnalysisStatus` instead of blind-polling, and each requested section is written out as its own JSON artifact. A run also belongs to the session that started it: `GetTraceAnalysisStatus` and `GetTraceAnalysisResult` find an `AnalysisId` only when they are called with the same `SessionId` as `AnalyzeTrace` was, and from any other session it reads as `NotFound` — deliberately the same answer as for an identifier that never existed, so neither command can be used to find out whether another caller's run exists. Omitting `SessionId` breaks this: the transport makes a fresh anonymous session per call, so a run started that way can never be looked up again. ⚠️ Attaching the raw `.utrace` (`StopTrace` with `AttachTraceFile: true`) always discloses the process command line whatever the channel set was, because it is written through an always-on internal channel — this is why it is gated by its own `RuntimeInsightsAttachTraceFile` capability, and why the analysis `Diagnostics` section (which reports a sanitised command line) is not equivalent to the file itself. The editor also enables the log, bookmark, region and screenshot channels by itself at startup, so in practice attaching a trace captured in the editor needs **both** `AllowLogDump=True` and `AllowDisclosingTraceAttachment=True`; `StartTrace` reports an `AttachDisabledByPolicy` warning up front when the channels it is about to record with would keep the file from being handed over. Stopping does not close the captured file on its own — the engine's trace writer finishes that on its own thread a moment later — so a `StopTrace` that asks for the file waits up to three seconds for it and reports `AttachSkippedReason: "TraceFileStillOpen"` if it is still being written by then, which is worth asking for again in a moment; a stop that did not ask for the file never waits. Demo build: only the 3 read-only trace commands are included; the analysis provider is compiled out entirely.

- **Asset audits run as a job instead of holding the game thread** (`UAIPEditorAssets` module): auditing a large content folder used to occupy the game thread until it finished, freezing the editor — and every other UAIP command — for tens of seconds to minutes, with no way for the caller to tell a working audit from a hung editor. Adds 3 read-only commands under `UAIP.Editor.Assets`: `StartAssetAudit` registers the job and returns an `AuditId` straight away, after which the scan advances a little at a time between editor frames while the editor stays usable and other commands keep being answered; `GetAssetAuditStatus` reports `State` (`Preparing` / `Running` / `Completed` / `Failed`), the report currently being scanned, processed and total counts, elapsed seconds, how many assets were skipped for disappearing mid-scan, and a failure reason; `GetAssetAuditResult` hands back one artifact per report once the job is `Completed`. All three require only `EditorInspect` — no new capability — and all three **require an explicit `SessionId`**, rejecting an anonymous one with `InvalidParams`, because a job started under a per-call anonymous session could never be polled or read afterwards. A job is visible only to the session that started it: an unknown, expired, or other-session `AuditId` all read as `NotFound`, deliberately indistinguishable. One audit runs at a time (`TooManyRequests` otherwise, naming the `AuditId` only when it is the caller's own), a start is refused with `NotAllowed` while the editor shows a modal dialog or a progress bar and paused rather than failed if one appears mid-scan, resubmission is rate limited per session and again across all sessions by how much editor time audits have consumed recently, and a job that has spent ten minutes of editor time is failed rather than left running (waiting time is not counted — consumed time is). A finished job is kept for 15 minutes, restarted on each successful read and capped at an hour from the start, and is dropped when the session ends, when Live Coding reloads, and when the editor stops — read the result before ending the session. How much of each frame a scan may take is configurable via `Config/DefaultUAIP.ini` → `[UAIP.Jobs] AuditStepBudgetMs` (default `10.0`, clamped to `[1.0, 100.0]`); see [Configuration → `[UAIP.Jobs]`](config.md#uaipjobs--per-frame-budget-for-job-style-commands). ⚠️ `FindUnreferencedAssets`, `FindCircularReferences`, `FindBrokenReferences` and `RunAssetAudit` are now `Deprecated`, with `StartAssetAudit` as their `MigrationTarget`. **They keep working exactly as they did** — same results, same progress firing — but they still hold the game thread for the whole audit, which is the reason to migrate. This also fixes a miscount in the circular-reference report: when the output limit was reached while examining the last root asset, the report said it had not been truncated. The cycles reported and their order are unchanged.

- **`AddAnimationToPoseSearchDatabase` gained an opt-in to bypass its own idempotency check** (`UAIPEditorMotionMatching` module). The command has always been idempotent for an animation already registered as a normal (non-BranchIn) entry — re-adding one reports the existing entry's `Index` instead of creating a second one — but that left no way to deliberately register the same animation more than once under different per-entry settings (a legitimate `UPoseSearchDatabase` use, and something the editor UI already allows). A new optional parameter, `bAllowDuplicate` (defaults to `false`), bypasses that check when set to `true`: the command always inserts a new entry, `InsertAt` and every settings field are applied the same way they are for a first-time add, and the response reports the new entry's `Index` with `bAlreadyPresent: false`. The default is unchanged — omitting the parameter keeps the existing idempotent behaviour exactly as before.

- **Typed ControlRig component editing — generic CRUD plus two typed domains** (`UAIPEditorControlRig` module): AI agents can now attach, inspect, and mutate ControlRig hierarchy components (`FRigBaseComponent` substructs) directly, instead of going through the generic hierarchy element commands. Adds 9 generic component commands under `UAIP.Editor.ControlRig` (`ListComponents`, `GetComponent`, `ListAddableComponentTypes`, `CanAddComponent`, `AddComponent`, `RemoveComponent`, `RenameComponent`, `ReparentComponent`, `SetComponentContent`) that work for every component type the module allowlist covers. Adds two typed domains on top of the same components: `UAIP.Editor.ControlRig.Dynamics` (16 commands — 6 typed reads, 6 typed writes, and 4 orchestration commands that build or rewire a whole solver / particle / constraint setup in one call; `Experimental`; requires the `ControlRigDynamics` plugin named explicitly in the `.uproject`; UE 5.8+ only) and `UAIP.Editor.ControlRig.Physics` (8 commands — 4 typed reads and 4 typed writes for the solver / body / joint / control types; `Stable`; requires the `ControlRigPhysics` plugin named explicitly in the `.uproject`; available on UE 5.7 as well as UE 5.8). Adds 1 DefaultDenied capability, `ControlRigComponentEdit`, required by every write across the generic commands and both typed domains — deliberately one capability for all of them, since creating a component with initial content reaches the same import path as replacing an existing one's content. Every write is rejected while PIE is running; the Physics domain's writes are also rejected against a ModularRig asset. ⚠️ `ControlRigDynamics` and `ControlRigPhysics` are each only reachable when their plugin is named **explicitly** in the `Plugins` array of the project's `.uproject` — a plugin the engine otherwise considers enabled (as `ControlRigPhysics` is, by default) does not register these commands.

- **Open and close arbitrary editor tabs by their Slate layout identifier** (`UAIPEditorWorkspace` module): AI agents previously had no way to open a tab that was not already open — `FocusEditorTab` only brings an already-open asset editor to the front, and driving the menu through `SelectMenuItem` reaches only tabs registered with the newer `UToolMenus` framework, so a tab reachable solely through a legacy `FMenuBarBuilder` menu was structurally unreachable. Adds 3 commands under `UAIP.Editor.Workspace`: `ListSpawnableTabs` (read-only; lists spawnable-tab candidates together with their owner identifier, display name, tooltip, and whether the tab is already open — read against the owner the row names, so a `Global` row answers for the whole editor rather than for one window, since a tab registered editor-wide docks wherever the layout puts it — the list is not exhaustive and says so), `OpenTabById` (opens a tab given its `TabId` and `OwnerTabId`, using an owner that is already open as it stands and opening the owner window first only when it is not, and reports whether it opened the owner itself so the caller knows what to clean up afterward — so every row the listing returns can be passed straight back in, including the panels inside an asset editor window), and `CloseTabById` (closes by the same pair of identifiers, taking an `InstanceId` when several instances of the same tab type are open). An `OwnerTabId` that matches several open windows at once is rejected with `InvalidParams` listing the candidates rather than guessed at; a tab the editor's own permission list rejects comes back as `NotAllowed` rather than the retried `ExecutionFailed`; and `OpenTabById` rolls back anything it opened (innermost first) when the target tab itself fails to come up. Adds 1 new DefaultDenied capability, `EditorTabSpawn`, required by all 3 commands — opening or closing an arbitrary tab can run third-party plugin code (`OnSpawnTab` / `OnCanCloseTab`, and the display-name / tooltip delegates the read-only list also has to call), so `ListSpawnableTabs` needs it too despite being read-only. ⚠️ Granting `EditorTabSpawn` lets an AI agent close **any** tab currently open, not only the ones it opened itself, and it can close a tab type the editor is configured to forbid **opening** — closing is deliberately exempt from that restriction so cleanup does not fail because of a display-permission change.

- **Writing references, structs and containers through the property commands — and editing one container element at a time** (`UAIPEditorShared` plus every module that writes properties): a property whose value is — or contains, at any depth — an object / class / soft / weak / lazy / interface reference, a delegate or a field path, and a property that is a struct outside the built-in value catalogue, an array, a set, a map, an optional or a fixed-size array, used to be refused **by type**, whatever the session held. Reading such a property always worked, so an AI agent could read a value and then had no way to write it back. Those writes are now governed by permission instead of being refused outright. Adds 2 DefaultDenied capabilities — `PropertyReferenceEdit` (the reference half; clearing a reference needs it too, since attaching and detaching a dependency are the same kind of change) and `PropertyStructuredEdit` (the struct / container half) — where a struct containing a reference needs **both**, so the structured one is never a way around the reference gate. Adds 4 optional parameters to 18 existing commands, with no new command and no signature change: `ValueJson` (the value as a JSON document instead of engine text, exclusive with the command's text value parameter), `Operation` (`Replace`, the default and exactly what these commands have always done, plus `Insert` / `Remove` / `Clear`), `ElementIndex` (the array position) and `ElementKeyJson` (the set element, or the map key). The commands are `SetActorProperty`, `SetAssetProperty`, `SetBlueprintDefault`, `SetWorldSetting`, `SetProjectSetting`, `SetDataTableRow` (`UAIP.Editor.Property`), `SetBlueprintComponentProperty`, `SetSectionProperty` (whose text parameter is `PropertyValue`), `SetSoundClassSettings`, `SetSoundAttenuationSettings`, `SetSoundMixSettings`, `SetSoundCueNodeProperty`, `SetDataflowNodeProperty`, `SetAnimNotifyProperty`, `SetPoseSearchSchemaChannelProperty`, and the three Subsonic property setters — `SetSubsonicEventActionProperty`, `SetSubsonicActionModifierProperty`, `SetSubsonicParameterValue` — whose `Value` is already a JSON value rather than engine text and which therefore take the three element-operation parameters but **no** `ValueJson`. A module that already governs reference writes through a capability of its own keeps that name for the reference half (`AnimNotifyReferenceEdit`, `DataflowReferenceEdit`, `SubsonicEventEdit`) while the struct / container half is always `PropertyStructuredEdit`, and a refusal always names the capability that command's own write path actually reads. `SetPCGNodeProperty`, `SetCustomCppPCGNodeProperty`, `SetCustomBlueprintPCGNodeProperty` and `SetConversationNodeProperty` already took their value as a JSON document and gain no element operations, but they no longer refuse references, structs and containers permanently either — those writes are gated by the same two capabilities. Element operations are idempotent where the container makes them so (adding an element a set already holds, removing one it never held), which is why the artifact reports `Changed` beside `Operation`; a container already holding more than 4096 elements is refused whatever the operation, `Remove` and `Clear` included, because the whole container is copied and validated before anything is committed. ⚠️ **A reference is never resolved by loading.** A hard reference names an object path that something already has loaded — "does not exist" and "exists but is not loaded" come back as the same refusal, because resolving without loading cannot tell them apart — while a soft reference is validated against the asset registry and needs nothing loaded. ⚠️ **References and composite values cannot be written as text**: passing an object path in `Value` is refused even with the capability granted, because the text import path would resolve and load the reference behind the capability gate. ⚠️ `SetPoseSearchSchemaChannelProperty` refuses a reference-bearing type outright with `PolicyViolation` and no capability lifts that, because writing a channel's sub-channel array directly would sidestep the class allowlist `AddPoseSearchSchemaChannel` enforces — add channels with that command instead. Because both capabilities are decided from the property's type while the write runs, neither appears in any command's declared `RequiredCapabilities`; see [Commands → Writing references, structs and containers](commands.md#writing-references-structs-and-containers).

- **Property reads now report what changing that property would take** (`UAIPEditorShared` plus the modules whose getters use it): the two capabilities above are decided from the property's type at write time, so they never appear in a command's declared `RequiredCapabilities` and `uaip_describe_command` cannot surface them — leaving an AI agent to discover them by being refused. Every property getter on the shared read path now attaches a `WriteRequirements` object beside the value it read: `RequiredCapabilities` (named as that command's own write path looks them up, so granting them actually unblocks the write), `HeldCapabilities` / `MissingCapabilities` (the same names split by what the session issuing the read holds), `IsWritable` / `RefusalReason` (whether the property's type and flags permit a write at all, whatever the session holds), and `WriteInputForm` (`TextOrJson` or `JsonOnly` — which input field the value belongs in). `GetAnimNotifyClassSchema` and `GetPoseSearchChannelClassSchema` attach the identical `WriteRequirements` object nested per property, so a struct, set or map either command can in fact write in the structured form is reported as writable rather than being called unwritable the way their own `bIsWritable` used to. A handful of commands decide writability on their own terms and attach no report; for those the refusal names the missing capability instead, so the guidance is what is absent, not the way forward. `GetCustomPCGNodeSchema`, `GetCustomBlueprintPCGNodeSchema` and `GetPCGNativeNodeSchema` still show a session without those capabilities exactly the curated set of types they showed before, but no longer omit the rest silently: they now report `HiddenCount`, `HiddenCapabilities` (which permissions would reveal them) and a `HiddenReasons` object whose `MissingCapability` / `Unwritable` keys are always present and always sum to `HiddenCount` — the same "what was left out" shape `uaip_list_commands` and `SnapshotUI` already use. The names of the hidden properties are still not disclosed.

- **`QueryCapabilities` now says which capabilities exist, not only which ones the session holds** (`UAIPCore` module): `Capabilities` — the effective set — and `OperationalConstraints` are unchanged, and the response gains `RegisteredCapabilityCount` and `UngrantedCapabilityCount`, plus — when called with the new `IncludeUnavailable: true` — `RegisteredCapabilities`, one entry per capability every loaded module has declared, carrying its `Name`, its `DefaultPolicy` (`Allowed` or `Denied`) and an `IsGranted` flag. The catalog is opt-in because it runs to well over a hundred entries and this is the command an agent is told to call first; the two counts are returned on every call, so a caller that never opts in still learns the catalog exists and how much of it this session cannot use, the same promise `uaip_list_commands` makes with `HiddenCount`. "Which capabilities would an operator have to enable?" is answered from the catalog alone — they are the entries whose `DefaultPolicy` is `Denied` — so no second field repeats those names. Until now a DefaultDenied capability could only be found through some command's declared `RequiredCapabilities`. That covers all of them except the two the property write path decides from the type of the property being written: no command declares `PropertyReferenceEdit` or `PropertyStructuredEdit`, so an AI agent had no way to learn they existed short of attempting a write and reading the refusal, or reading a property's `WriteRequirements` — it could not plan around a permission it had no way to name. The catalog is deliberately **not** narrowed by the session's bound role: a role-restricted session sees the names with `IsGranted: false`, which is what lets it ask an operator to enable one or understand why an expected command is missing, while the role still denies the operation itself. Only capability names and their default policies are disclosed — no values, and nothing about the project's contents.

- **Four module-specific reference capabilities** (`UAIPEditorUMG`, `UAIPEditorEnhancedInput`, `UAIPEditorStateTree`, `UAIPEditorNiagara` modules): `WidgetSlotReferenceEdit`, `EnhancedInputReferenceEdit`, `StateTreeParameterReferenceEdit` and `NiagaraReferenceEdit` — all DefaultDenied — gate reference writes on `SetSlotProperties`, on the four Enhanced Input trigger / modifier setters, on `SetStateTreeParameter`, and on a reference-typed parameter default passed to `AddSetParameterEntry` / `AddSetParametersModule` respectively, following the same module-owns-its-reference-capability pattern as `AnimNotifyReferenceEdit` and `DataflowReferenceEdit`. Writing a struct or container on the same properties additionally requires `PropertyStructuredEdit`. **Changed**

> **Why none of this is MAJOR.** This release changes behavior in a few places, but none of them crosses the line into a SemVer MAJOR change. Each case is either a fix to a contract that was documented but never actually reachable, a specification change to a command marked `Experimental`, or a fix to behavior that contradicted its own declared contract. A `Stable` command whose declared, reachable behavior actually changes is always MAJOR, regardless of the reason for the change.

- **Command parameters are now type-checked against the schema the handler declares** (`UAIPCore` module). Until now only unknown properties and missing required fields were enforced, and the value itself went straight to `FJsonObject::TryGet*Field`, whose implicit conversions accept almost anything — `"yes"` reached a handler as the boolean `true`, and `"abc"` reached it as the integer `0`. Every supplied value is now checked against the declared `Type` before dispatch, and a mismatch is rejected with `InvalidParams` naming the expected and actual type. Array elements are checked against `Items.Type` one level deep, `Integer` additionally requires no fractional part, JSON `null` is treated as "not supplied" so handler-side defaulting is unaffected, and an unrecognised type keyword imposes no constraint. ⚠️ **Behavior change — check your calls if you relied on the old coercion** — most visibly in scenarios, where the type-preservation rule means a numeric `Variables` entry spliced into a String parameter arrives as a number: `"Variables": { "ExpectedHp": 100 }` feeding `AssertActorProperty`'s `ExpectedValue` must now be written `"ExpectedHp": "100"`.
- **`FocusEditorTab` and `CloseEditorTab` renamed their `TabId` parameter to `AssetPath`** (`UAIPEditorWorkspace` module). ⚠️ **Behavior change — check your calls to these two commands** — `TabId` is now rejected with `InvalidParams`. Both commands have always resolved their target as an asset path, so the old name invited callers to pass the `ActiveTabId` that `DumpEditorState` reports, which is a Slate layout identifier and could never resolve. The old name is rejected rather than accepted as an alias, because a silently ignored `TabId` would fail later and further from the cause. `CaptureEditorTabImage` keeps its `TabId`, which really is a layout identifier.
- **`CaptureActiveWindowImage` no longer requires the editor to be the foreground application** (`UAIPEditorObservation` module): the command previously failed whenever another application was in front, because Slate reports no active top-level window until Windows sends a real activation message — an editor launched by the MCP bridge while the user works elsewhere never gets one. Screenshots do not read the screen, so the background editor was always capturable; the command now falls back to the editor's main window and reports which one the image is of in `Result.CapturedWindow` (`"ActiveWindow"` / `"MainWindow"`). The fallback only reaches the main window, so a floating asset editor or modal dialog still needs `CaptureEditorTabImage` while another application is in front.
- **`CaptureEditorTabImage` now resolves tabs owned by a nested tab manager** (`UAIPEditorObservation` module): identifiers such as `LevelEditorViewport` name minor tabs belonging to a major tab's own manager, so the previous global-only lookup rejected most of the values `DumpEditorState` reports as `ActiveTabId`. Its documentation already told callers to pass that value straight through; the lookup now matches. Note that capturing brings the named tab to the front of its stack — a tab behind a sibling is not drawn and would come back empty — so capturing changes which tab the user sees.
- **Scenario template pointers now have a settled grammar, and a failed resolution says why** (`UAIPScenario` module). A step could not splice a bridge command's response into a later step: the tokenizer rewrote every `.` in the pointer to `/`, so a body written with a leading slash became `//refPath` and missed, while the guides disagreed about which spelling was right. The pointer body now has two readings, told apart by the first character — a body opening with `/` is taken as a literal JSON pointer, which is the only way to reach a key containing `.`; any other body keeps treating `.` and `/` alike, so **every pointer that resolved before still resolves**. `${StepName.Data}` with no pointer now addresses the whole object. ⚠️ **Behavior change for pointers that used to hit by accident** — object keys are now matched case-sensitively (`Data.refPath` and `Data.RefPath` are no longer the same key), array indices accept only `0` or a non-zero digit run (`01`, `+1`, `1abc` are rejected), `~1` and `~0` now decode as RFC 6901 escapes (a key containing a literal `~` must be written `~0`), and an object or array referenced from inside a larger string now fails instead of quietly becoming an empty string. Resolution failures now report which kind of failure occurred — a misspelled step name, a missing variable, a pointer that did not match, or a malformed escape each get their own sentence — and the error code moved from `ExecutionFailed` to **`InvalidParams`**, which also means these failures are **no longer retried** by `RetryCount`. Values spliced from step data are size-checked, objects and arrays are copied rather than shared with the recorded step result, and the whole params tree now resolves against a byte budget charged on expansion growth.
- **Command parameters across five modules renamed to their PascalCase spelling — and they now actually reach the handler** (`UAIPEditorSequencer`, `UAIPEditorUIAutomation`, `UAIPEditorPhysics`, `UAIPEditorGameFeatures`, `UAIPEditorEnhancedInput` modules). Each of these parameters was advertised in the command schema under one spelling while the parser read a different one, so **neither spelling ever worked**: the advertised name passed schema validation and was then silently dropped, leaving the parameter at its default, and the spelling the parser wanted was rejected up front with `InvalidParams` because these schemas declare `AdditionalProperties: false`. The schema now advertises exactly the name the parser reads, so these parameters are usable for the first time. Renamed:
  - `UAIP.Editor.Sequencer` — `bDeferNotification` → `DeferNotification` on `AddKeyframe`, `AddSection`, `AddTrack`, `BindActor`, `RemoveKeyframe`, `RemoveSection`, `RemoveTrack`, `SetKeyframeValue`, `SetPlaybackRange`, `UnbindActor`; `bRemoveAll` → `RemoveAll` on `RemoveKeyframe`.
  - `UAIP.Editor.UIAutomation` — `bStopOnFirstError` → `StopOnFirstError` on `FillForm`.
  - `UAIP.Editor.Physics` — `offset_x` / `offset_y` / `offset_z` → `OffsetX` / `OffsetY` / `OffsetZ` on `SetBox`, `SetCapsule`, `SetSphere`; `constraint_mode` → `ConstraintMode` on `AddConstraint`.
  - `UAIP.Editor.GameFeatures` — `plugin_name` → `PluginName` and `output_path` → `OutputPath` on `CreateGameFeaturePlugin`; `plugin_name` → `PluginName` and `plugin_url` → `PluginUrl` on `GetGameFeatureInfo`; `filter_state` → `FilterState` on `ListGameFeatures`.
  - `UAIP.Editor.EnhancedInput` — `path_filter` → `PathFilter` on `ListInputActions` and `ListMappingContexts`.

  ⚠️ **Two things change for existing callers, and neither is a loss of working behaviour.** First, a call that sent one of the old names is now rejected with `InvalidParams` instead of being accepted and ignored — the value it sent never had any effect, so replacing the spelling is the whole fix. Second, a call that sends the new name now gets the documented behaviour rather than the default the command silently used before: `DeferNotification` really defers the Sequencer notification, `RemoveAll` really selects the removal scope, `StopOnFirstError` really stops `FillForm` at the first failing field, `OffsetX` / `OffsetY` / `OffsetZ` are really applied to the shape, and the GameFeatures / EnhancedInput filters really filter. `UAIP.Editor.Niagara` is not part of this entry; its parameters are covered by the Niagara entry immediately below.

- **Every `UAIP.Editor.Niagara` parameter and artifact field is now spelled in PascalCase** (`UAIPEditorNiagara` module). The module carried two parallel sets of key constants — one PascalCase, used by the observation and topology commands and by every field the Niagara inspector writes into an artifact, and one snake_case, used by the editing commands added later — so the same logical field reached callers under two different names depending on which command produced it. The clearest symptom: `CompileNiagaraSystem` wrote its result as `compile_state` / `compile_errors` while `GetSystemCompileState` wrote the very same two fields as `CompileState` / `CompileErrors`, so no single key read both. The two sets are now one, and every key in the module is PascalCase. Each name below applies wherever it appears in the module — as a command parameter, as an artifact field, or as a field of an object inside the `Parameters` / `Variables` arrays:
  - Target identity — `asset_path` → `AssetPath`, `asset_type` → `AssetType`, `asset_name` → `AssetName`, `emitter_id` → `EmitterId`, `emitter_name` → `EmitterName`, `emitter_asset_path` → `EmitterAssetPath`, `module_id` → `ModuleId`, `module_name` → `ModuleName`, `script_path` → `ScriptPath`, `script_name` → `ScriptName`, `script_usage` → `ScriptUsage`, `stack_usage` → `StackUsage`, `input_name` → `InputName`, `parameter_name` → `ParameterName`, `enum_path` → `EnumPath`.
  - Values and options — `insert_index` → `InsertIndex`, `new_index` → `NewIndex`, `new_name` → `NewName`, `timeout_seconds` → `TimeoutSeconds`, `type_name` → `TypeName`, `type_path` → `TypePath`, `default_value` → `DefaultValue`, `variable_name` → `VariableName`, `variable_names` → `VariableNames`, `renderer_class_path` → `RendererClassPath`, `renderer_index` → `RendererIndex`, `local_space` → `LocalSpace`, `warmup_time` → `WarmupTime`.
  - Blueprint wrapper — `actor_identifier` → `ActorIdentifier`, `component_name` → `ComponentName`, `target_blueprint_path` → `TargetBlueprintPath`, `parent_class_path` → `ParentClassPath`, `blueprint_path` → `BlueprintPath`.
  - Artifact-only fields — `compile_state` → `CompileState`, `compile_errors` → `CompileErrors`, `requires_followup_compile` → `RequiresFollowupCompile`, `parsed_as_default` → `ParsedAsDefault`, `parsed_as_default_array` → `ParsedAsDefaultArray`, `variable_count` → `VariableCount`.
  - Differing only in case, and therefore still accepted under the old spelling — `kind` → `Kind`, `value` → `Value`, `force` → `Force`, `enabled` → `Enabled`, `name` → `Name`, `properties` → `Properties`, `parameters` → `Parameters`, `variables` → `Variables`, `determinism` → `Determinism`, `success` → `Success`.

  ⚠️ **Behavior change for every name in the first four groups.** JSON key matching in the engine is case-insensitive, which is why the last group keeps working under its old spelling — but the other names differ by more than case, so a request that sends the old one is now rejected with `InvalidParams` (these schemas declare `AdditionalProperties: false`), and code that reads an artifact by an old field name finds nothing. Replacing the spelling is the whole fix: no command, capability, value, or behaviour changed beyond the names. The `Toolset.Editor.Niagara.*` bridge commands are untouched — they forward the engine's own Toolset schema and keep its spelling. This also fixes `AddSetParametersModule` advertising the item schema for its `Parameters` array under `items` rather than `Items`, which kept `uaip_describe_command` from showing callers the shape of an entry.

- **`ReadOnly` no longer refuses `ShutdownEditor` and `RestartEditor`** (`UAIPCore` and `UAIPEditorWorkspace` modules). `ReadOnly=True` rejected every mutating command, and the two editor lifecycle commands are mutating — so an editor launched under that policy could not be stopped or restarted through UAIP at all, and because the policy is read at launch, editing the ini did not reach the running process either. What was left was closing the editor by hand or killing the process, which is what the documentation tells operators not to do and what leaves the plugin DLL locked. Both commands are now exempt from the read-only refusal and are reported as `Available: true` under it; nothing else about `ReadOnly` changes, their optional `SaveAll` is still governed by `DisableSave`, and no other command declares the exemption. ⚠️ **`EditorLifecycle` is DefaultAllow**, so on an otherwise untouched configuration `ReadOnly=True` now leaves the AI able to stop and restart the editor. #### MCP Bridge

Unreleased since MCP Bridge 1.1.2. The bridge is versioned and released independently of the plugin; see the version numbering above.

**Added**

- **Progress notifications while a `uaip_execute` call is pending.** When the client attaches an MCP progress token to the call, the bridge now sends a `notifications/progress` update about every 5 seconds until the call returns, carrying the seconds elapsed and the editor's state (`STARTING` / `RUNNING` / `UNRESPONSIVE`). It reports nothing from inside the editor — a job's own progress is read with the command that knows it, such as `GetAssetAuditStatus` — and `uaip_run_scenario` is out of scope. With no token nothing is sent. ⚠️ **Whether the update is ever shown is the client's decision**, and a client that ignores `notifications/progress` displays nothing while the call is pending; Claude Code is one such client as of this writing. See [Connections → Progress notifications while a call is pending](connections.md#progress-notifications-while-a-call-is-pending).
- **`uaip_get_editor_status` now reports the lock file's state.** The response gains a `Data.Lock` object — whether a lock file exists, whether this bridge holds it, the port / project / timestamp it records, and whether that recorded port currently has something listening on it — so a launch blocked by another bridge's lock can be diagnosed without deleting anything. See [Connections → Lock diagnostics](connections.md#lock-diagnostics).

**Fixed**

- **A shutdown the editor refused was reported as a success.** `ShutdownEditor` returned `{"Success": true}` without ever reading what the editor answered, so a refusal — a read-only safety policy declining the command, for instance — looked like a clean shutdown while the process kept running and kept holding its file locks. The bridge now forwards the editor's own error, and confirms the port has actually been released before saying the editor stopped; when it cannot tell, it says so rather than guessing.
- **A restart left the bridge unable to talk to the editor at all.** `RestartEditor` is the editor relaunching itself, so the successor is not a process the bridge started. The bridge went on holding the dead handle and refused every later command with "the port is occupied by a process that is not this project's editor" — permanently, because that refusal cleared no state. Recovering meant closing the editor by hand. The bridge now adopts the editor answering on the port, after checking it reports the same project.
- **A response cut short no longer restarts a healthy editor.** A connection that dropped mid-response and one that never opened were classified the same way, so the bridge could restart an editor that was working and resend a request it had already begun. The two are now told apart, and a dropped response only counts as a dead editor when the port has genuinely gone.
- **A long command no longer looks like a dead editor.** The bridge pings every 15 seconds and declared the editor stopped after 30 seconds of silence, but a command that holds the game thread for longer than that — `BuildMetaHuman` takes about 75 seconds — starved those pings. The bridge would then either launch a second editor against the same project or terminate the healthy one that was still working.
- **A scenario template with a leading slash no longer misses.** The pointer tokenizer rewrote every `.` to `/`, so a body written as `${S.Data./refPath}` became `//refPath` and matched nothing. A body opening with `/` is now read as a literal JSON pointer — the only way to reach a key that itself contains `.` — while any other body keeps `.` and `/` as interchangeable separators. A failed resolution also names which part failed instead of returning one fixed sentence for every cause.
- **A running editor could be judged stopped, handing its lock to a second bridge.** The bridge checked whether the lock holder's process id was alive with `os.kill(pid, 0)`. On Windows that call raises **the same error** whether the process does not exist or exists but cannot be queried, and the bridge read it as the former — so the process holding a running editor could be written off as gone. Two bridges holding the same lock drive the same editor at once, which crosses commands and can end the editor unexpectedly. The bridge now queries the process directly and reads its exit code, treating "cannot be queried" as proof that the process exists.
- **A bridge no longer driving an editor kept holding the project lock, blocking every other session from launching one.** The lock was only released on a clean shutdown; if the bridge was force-terminated, or if it simply stopped driving an editor without exiting itself (the editor was closed or restarted from elsewhere), the lock stayed marked as held, and every other bridge trying to launch that project's editor was refused with "another mcp_proxy instance is already managing this project" — with no way out short of deleting the lock file by hand. The bridge now releases the lock as soon as it notices it is no longer driving an editor (unless it is waiting out a restart it requested itself), and a force-terminated bridge no longer leaves the lock stuck either, since the OS releases the underlying file handle the moment that process ends. A lock file that is merely present but held by nobody is simply overwritten by the next bridge to start — it is not itself a problem anymore.

**Changed**

- **Artifacts that will not be inlined are no longer downloaded.** The bridge fetched an artifact's bytes and then decided whether its MIME type was on the inline allowlist. It now reads the length and content type first and fetches the body only when it is going to be used, which matters most for the binary artifacts the allowlist excludes by design — a `.utrace` capture can be hundreds of megabytes.

**Changed**

- **`UAIP.Runtime.World.GetConsoleVariable` and `UAIP.Runtime.World.SearchConsoleVariables` deprecated**: Use `UAIP.Runtime.Engine.CVar.GetConsoleVariable` and `UAIP.Runtime.Engine.CVar.SearchConsoleVariables` instead. Both commands remain functional and return `Success: true` with a `DeprecationWarning` in the response `Data`.
- **`UAIP.Core.ListPlugins` deprecated**: Use `UAIP.Runtime.Engine.Plugin.ListPlugins` instead. The original command remains functional but will be removed in a future release.
- **Niagara module now supports UE 5.7**: All commands under `UAIP.Editor.Niagara` and `UAIP.Runtime.Niagara` (36 UAIP + Toolset bridge commands) are now available on UE 5.7. Previously the entire module was unregistered on UE 5.7 and every command returned `CommandNotFound`.
- **Niagara `default_value` applied**: `AddSetParametersModule` and `AddSetParameterEntry` now parse and apply the `default_value` field for common types (float, int, bool, `UScriptStruct`). Previously entries were always created with type defaults regardless of the supplied value.
- **`script_name` now required for `AddSetParameterEntry` / `RemoveSetParameterEntry`** *(breaking)*: Both commands require a new `script_name` parameter (e.g. `Spawn`, `Update`, `Particle Spawn`, `Particle Update`). This parameter routes the call to the correct script stack and is necessary for the UE 5.8 External Edit API. Existing calls without `script_name` will return `InvalidParams`.
- **`UAIP.Editor.Engine.ConfigSettings.SetSettingsValues` `DryRun` `ValueType` format migrated** (`UAIPEditorEngineManagement` module): The `WouldChange[].ValueType` field in the `DryRun=true` response now uses the same type-string format as `GetSettingsSchema` (`enum:EMyEnum`, `struct:FMyStruct`, `TArray`, `TMap`, `TSet`, `UObject*:UMyClass`, `uint8`) instead of falling back to the raw C++ type name for these categories. This consolidates a previously duplicated (and less complete) type-name mapping onto the shared `FPropertySchemaSerializer` utility already used by `GetSettingsSchema`. `SetSettingsValues` is `Stability: Experimental`, so this format change ships as a non-breaking update per the Experimental exception in the versioning policy; scalar types (`bool`, `int32`, `int64`, `float`, `double`, `FString`, `FName`, `FText`) are unaffected.

**Fixed**

- **PIE/SIE mutation guard consolidated and corrected across 9 editor-domain modules** (Foliage, WorldPartition, Level, PCG, Niagara, Sequencer, Property, Physics, UMG): the duplicated per-module PIE/SIE rejection logic and editor-world lookup were consolidated into a single shared implementation, fixing several latent bugs found in the process:
  - `SetActorProperty` / `SetWorldSetting` previously had **no PIE/SIE guard at all** and could mutate the editor world while Play-In-Editor or Simulate-In-Editor was active. `GetActorProperty` / `GetWorldSetting` are unaffected and continue to succeed during PIE/Simulate.
  - The Toolset-bridge validation helper used by Niagara, Physics, and UMG commands never detected Simulate-In-Editor, only Play-In-Editor — Simulate-time mutations could slip through.
  - `SetActorTransform`, `PlaceActorInLevel`, `DeleteActorFromLevel` (Level) and the WorldPartition/DataLayer/HLOD mutation commands returned `ExecutionFailed` instead of `NotAllowed` when rejected during PIE/Simulate *(breaking for callers that pattern-match on `ExecutionFailed` for this case)*; the ErrorCode is now `NotAllowed`, matching every other domain.
  - `GetPCGGraphInfo` and `GetSequenceInfo` continue to report PIE/Simulate state as a plain boolean field in their response and are not blocked during Play/Simulate.
- **`uaip_run_scenario` `Variables` field now resolves through `${Variables.<key>}` templates**: the top-level `Variables` map passed to a scenario was parsed but never loaded into the step execution context, so any step referencing `${Variables.<key>}` always failed with `ExecutionFailed: Template resolution failed.` across every transport (HTTP, MCP, CLI, WS). Initial variables are now loaded before the first step dispatches, so they are visible (with type preserved) from the first step onward. A `Variables` payload that exceeds the per-scenario variable count or per-value size limit is now rejected up front with `InvalidParams` instead of silently dropping the offending entry.
- **`SetConsoleVariable` / `ResetConsoleVariable` now reject cheat-flagged (`ECVF_Cheat`) CVars by default**: previously only `ECVF_ReadOnly` was checked, so any CVar writable via `RuntimeCVarWrite` could be mutated regardless of its `ECVF_Cheat` flag. A new `AllowCheatCVarWrite` SafetyPolicy switch (default `False`) now gates cheat-flagged writes, returning `PolicyViolation` when disabled; `ECVF_ReadOnly` continues to take precedence (`NotAllowed`) over the cheat check. Successful writes now report a `WasCheatCVar` boolean in both the artifact and the command result.
- **Physics native handlers migrated to the shared PIE/SIE guard** (`UAIPEditorPhysics` module): all 31 native commands under `UAIP.Editor.Physics` previously implemented their own inline PIE/SIE check instead of the shared implementation described above, with the rejection message split across three inconsistent variants. The 21 write commands (`AddBody`, `SetBox`, `SetCapsule`, `SetSphere`, etc.) now use the shared guard with a single unified message; their behavior during PIE/Simulate is unchanged. The 10 read-only commands (`GetBodyNames`, `GetBodyShapes`, `GetConstraints`, `GetPhysicsAssetSummary`, `ValidatePhysicsAsset`, etc.) — which only load the `PhysicsAsset` from disk and never touch the live world — no longer reject during PIE/Simulate *(breaking for callers that relied on `NotAllowed` in that case)*; their response now includes a `PieInProgress: true` field when called during Play/Simulate, matching the plain-boolean pattern used by `GetPCGGraphInfo` / `GetSequenceInfo` above.
- **`bSkipCompile` now actually applied for `UAIP.Editor.SoundCue.*` commands** (`UAIPEditorSoundCue` module): `CompileSoundCue`, `AddSoundCueNode`, `RemoveSoundCueNode`, `ConnectSoundCuePins`, and `DisconnectSoundCuePins` all document a `bSkipCompile` parameter in their schema, but the parser looked up the wrong internal key, so any value sent by a caller was silently ignored and the graph was always recompiled. `bSkipCompile: true` now correctly skips the compile step.
- **Several `b`-prefixed parameters and response fields silently ignored due to a JSON key mismatch** (`UAIPEditorGameplayTags`, `UAIPEditorMaterial` modules): input parameters advertised in the command schema — `bIncludeNative`, `bAllowNonRestrictedChildren`, `bForceRemoveChildren`, `bUpdateAssetReferences`, `bFallbackToFullScan` on GameplayTag commands; `bSkipCompile`, `bAllowParameterDeletion` on Material commands — were parsed against an internal key missing the `b` prefix, so any value sent by a caller was silently dropped and the parameter always fell back to its default. The same mismatch affected several boolean response fields, which always reported their default regardless of the actual result: `bIsNative`, `bIsRestrictedTag`, `bRedirectAdded`, `bCodeReferencesNotDetected`, `bTruncated` on GameplayTag commands; `bTruncated`, `bHasInvalidCoords`, `bConnected`, `bAlreadyConnected`, `bRequiresFollowupCompile`, `bIsParameter`, `bHasErrors` on Material commands. All of the above now read and write the correct key.
- **Float/double property values no longer padded to 6 decimal places** (`UAIPEditorShared` module; affects any command reading a float/double property, e.g. `GetActorProperty`, `GetWorldSetting`, DataTable row reads, Blueprint default reads): previously formatted via a generic `%f`-based fallback (`9.5` → `"9.500000"`); now uses `FString::SanitizeFloat` (`9.5` → `"9.5"`), matching the format already used elsewhere in the API.
- **`EndSandboxSession`'s `DiscardPending` parameter now rejects non-boolean values** (`UAIPEditorSandbox` module): previously used a loose bool coercion that silently accepted any JSON string (e.g. `"yes"` became `true`); it now requires an actual JSON boolean and returns `InvalidParams` otherwise.
- **`FindCueNotifyAssets`'s `CueTag` parameter now validates the `GameplayCue.` prefix** (`UAIPEditorGAS` module): matching its sibling commands (`AddCueTag`, `RemoveCueTag`, `ExecuteCueOnSelectedActor`), a non-empty `CueTag` not starting with `GameplayCue.` now returns `InvalidParams` instead of being silently accepted.
- **ErrorCode corrected for several commands** (`UAIPEditorUMG`, `UAIPEditorNiagara`, `UAIPEditorPCG` modules): `AddWidget`, `GetWidgets`, and `SetSlotProperties` now return `ExecutionFailed` (previously `NotFound`) when the target WidgetBlueprint fails to load, matching every other UMG command's convention; `RemoveSetParameterEntry` now returns `ExecutionFailed` (previously `NotFound`) when the underlying Niagara system fails to load; `UpdatePCGCommentBox` now returns `NotFound` (previously `ExecutionFailed`) when the target comment box's GUID cannot be resolved, matching `RemovePCGCommentBox`.
- **`GetItems` secret-field masking now works correctly for nested `FInstancedStruct` fields on UE 5.7** (`UAIPEditorDataRegistry` module): UE 5.8 added a dedicated JSON-object export path for `FInstancedStruct` that UE 5.7 lacks (it serializes as a plain string instead), which the masker did not account for — on UE 5.7, a secret field nested inside an `FInstancedStruct` value could be returned unmasked. The masker now fails secure and masks the entire field when it cannot inspect the struct's individual properties.
